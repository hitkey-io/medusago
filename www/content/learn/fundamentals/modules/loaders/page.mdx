# {metadata.title}

In this chapter, you'll learn about loaders and how to use them in a module.

## What is a Loader?

When you start the MedusaGo application, the modules it uses are loaded: each one builds its service and registers it in the [container](!docs!/learn/fundamentals/medusa-container). Modules also run their loaders at certain points.

A loader is a function that a module defines to run code when the module is loaded. Use loaders to perform one-time setup, such as seeding the module's tables with default data, or checking that the module's configuration is valid.

MedusaGo's own modules use loaders for the same purposes. For example, the Currency Module's loader inserts the list of currencies, and the Region Module's loader inserts the list of countries.

---

## How to Create a Loader?

### 1. Implement Loader Function

A loader is a function of type `Loader`, which receives a context and a `LoaderOptions` value:

| Field | Description |
| --- | --- |
| `DB` | The database handle of the module. |
| `Options` | The [options](!docs!/learn/fundamentals/modules/options) of the module, as a `map[string]any`. |
| `Providers` | The providers registered for the module, for modules that have providers. |
| `Logger` | A `*slog.Logger`. |

A loader doesn't receive the container. To use the module's data models, build a service over them with `NewMedusaService` and use the internal service of the data model.

Run the migrations, which run the loaders of every module:

```bash

```

## When are Loaders Executed?

### Loaders Executed with Migrations

MedusaGo runs the loaders of the modules after it runs the migrations and syncs the links, in these commands:

- `go run . db:migrate`
- `go run . db:setup`, which runs the same steps as `db:migrate`, after it creates the database.
- `go run . db:migrate:scripts`

The loaders run in the order the modules appear in the application's configuration.

### Loaders Executed on Application Startup

A loader doesn't run when the application starts unless the module asks for it. The built-in modules whose loaders insert required data, such as the Payment Module, ask for it. Set `LoadersOnStart` to `true` on the module's exports to do the same:


The loaders of the module then run each time the application starts, after the modules' services are created.

<Note>

Medusa runs the loaders of every module when the application starts. MedusaGo only does so for the modules that set `LoadersOnStart`, and for all modules when you run the migration commands above.

</Note>

## Avoid Heavy Operations in Loaders

A loader that runs on startup delays the start of the application, and a failing loader stops it. Keep such loaders fast and make them tolerate a temporary failure.

The loaders of MedusaGo's own modules return `nil` after they log a warning when they can't insert their data, so that the application can still start. Return an error from a loader only when the module can't work without what the loader does.

### Alternative Solutions

If you need to run heavy work, consider these alternatives:

- A [scheduled job](!docs!/learn/fundamentals/scheduled-jobs), to run the work periodically.
- A [custom CLI script](!docs!/learn/fundamentals/custom-cli-scripts), to run the work when you decide to.
- A [workflow](!docs!/learn/fundamentals/workflows), to run the work in the background.
