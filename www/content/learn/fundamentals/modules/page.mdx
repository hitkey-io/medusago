# {metadata.title}

In this chapter, you'll learn about modules and how to create them in your MedusaGo application.

## What is a Module?

A module is a reusable package of functionalities related to a single feature or domain. MedusaGo integrates the module into your application without implications on the existing setup, since the module is isolated from the rest of the application.

For example, MedusaGo's [Commerce Modules](!resources!/commerce-modules) are modules for commerce features, such as products, carts, or orders. You can also create custom modules to add features specific to your business, such as a blog or a loyalty programme.

A module has:

- [Data models](!docs!/learn/fundamentals/data-models) that represent its tables in the database.
- A service, a Go type that holds the module's business logic: it creates, reads, updates, and deletes the module's data, and exposes any custom method you add.
- Optionally, [migrations](!docs!/learn/fundamentals/data-models/write-migration), [loaders](!docs!/learn/fundamentals/modules/loaders), and [options](!docs!/learn/fundamentals/modules/options).

MedusaGo registers the module's service in the [container](!docs!/learn/fundamentals/medusa-container) under the module's key, so you can use it in API routes, workflows, and scripts.

<Note>

MedusaGo modules are written with the same building blocks as Medusa's: DML data models, a service generated by `MedusaService`, and migrations. If you've written a Medusa module, only the language changes.

</Note>

## How to Create a Module?

In this section, you'll build a Blog Module that stores blog posts, their comments, and their tags. You'll create it as a Go package at `src/modules/blog` in your application.

<Note>

The snippets in this chapter leave out the `import` block of the files that import other packages of the module. The import paths of your own packages start with the Go module path of your application. The import paths of MedusaGo's packages are the ones shown in the snippets that include them.

</Note>

### 1. Create Data Model

A data model represents a table in the database. You create it with the [Data Model Language (DML)](!docs!/learn/fundamentals/data-models), the `dml` package of MedusaGo.

Create the file `src/modules/blog/models.go` with the following content:

```go title="src/modules/blog/models.go" file="modules/blog/models.go"
```

You define the `Post` data model with the `dml.Define` function. Its first argument is the name of the table. The second argument is the model's schema: the list of its properties, in order. `Comment` and `Tag` are related to `Post`, which you'll learn about in the [Relationships](!docs!/learn/fundamentals/data-models/relationships) chapter.

`Models` lists the data models of the module. You'll pass it to the module definition.

Learn more about data models in the [Data Models chapter](!docs!/learn/fundamentals/data-models).

### 2. Create Service

You create the module's main service in the file `src/modules/blog/service.go`. The service is a struct that embeds `*MedusaService`, the [service factory](!docs!/learn/fundamentals/modules/service-factory). Embedding it gives your service methods to manage the records of every data model, without writing them yourself.

For example, create the file `src/modules/blog/service.go` with the following content:

```go title="src/modules/blog/service.go" file="modules/blog/service.go" region="service"
```

The `BlogModuleService` struct embeds `*utilsmodulessdk.MedusaService`. The `options` field holds the [module's options](!docs!/learn/fundamentals/modules/options), which you set in the module's configuration in a later step.

You add your own methods to the struct, next to the ones the service factory gives it. For example, the `CreateDraft` method of the Blog Module creates a post whose title is no longer than the configured limit.

Learn more about the service factory in the [Service Factory chapter](!docs!/learn/fundamentals/modules/service-factory).

### 3. Export Module Definition

The final piece of a module is its definition. It tells MedusaGo which data models and service the module has. You create it in the file `src/modules/blog/index.go`:

```go title="src/modules/blog/index.go" file="modules/blog/index.go" region="module"
```

You call the `Module` function with:

1. The module's name: `"blog"`. It's the key under which MedusaGo registers the module's service in the container, and the name of the module in the configurations. It's also the prefix of the names of the module's events, such as `blog.post.created`.
2. The module's definition, a `ModuleDefinition` with the following fields:

| Field | Description |
| --- | --- |
| `Models` | The module's data models. |
| `Migrations` | The module's [migrations](!docs!/learn/fundamentals/data-models/write-migration), in the order they run. |
| `Loaders` | The module's [loaders](!docs!/learn/fundamentals/modules/loaders). |
| `Service` | A function that builds the module's service. It receives the generic `MedusaService` of the models, which you wrap in your own service. Without it, the module's service is the generic `MedusaService`. |

The `Module` function and `ModuleDefinition` are in the `modules-sdk` package of `utils` (`github.com/hitkey-io/medusago/packages/core/utils/src/modules-sdk`). `Loader` and `ServiceOptions` are in the `modules-sdk` package of `types` (`github.com/hitkey-io/medusago/packages/core/types/src/modules-sdk`).

`Module` returns a `*DefinedModule`. Its embedded `ModuleExports` is what you register in the configuration, and its `Linkable` field is what you use to [link the module's data models](!docs!/learn/fundamentals/module-links) to other modules.

<Note type="warning">

`Module` panics when it starts if a data model is invalid, for example when a relationship points to a model that the module doesn't define.

</Note>

### 4. Add Module to MedusaGo's Configurations

To use the module in your application, add it to the `Modules` of the configuration in `medusa-config.go`:

```go title="medusa-config.go" file="modules/app/medusa-config.go" region="config"
```

The `config` package is `github.com/hitkey-io/medusago/packages/core/framework/src/config`. The configuration of a module has these fields:

| Field | Description |
| --- | --- |
| `Module` | The module's exports: the `ModuleExports` embedded in the result of `Module`. |
| `Resolve` | The path to the module's directory, relative to the application's directory. `db:generate` writes the module's migrations in its `migrations` directory. |
| `Key` | The key of the module in the container. It's optional, and defaults to the module's name, `blog`. |
| `Options` | The module's [options](!docs!/learn/fundamentals/modules/options). |

<Note title="Limitations">

A module of your application can only be registered with Go code, as `ModuleConfig.Module` isn't part of the JSON and YAML formats. The stock `medusa` binary, which reads `medusa-config.json` or `medusa-config.yaml`, only loads the modules that ship with MedusaGo. Learn more in the [Configurations chapter](!docs!/learn/configurations/medusa-config).

</Note>

### 5. Generate Migrations

A migration is a change to the database's schema, with the SQL statements that apply and revert it. To create the tables of the module's data models, you generate a migration with the `db:generate` command.

MedusaGo's migrations are Go values. The command writes them in a `migrations` package inside the module, and you reference the list of migrations in the module's definition. So, before you run the command for the first time, create the package with an empty list. Create the file `src/modules/blog/migrations/index.go`:

```go title="src/modules/blog/migrations/index.go" file="modules/blog/migrationstub/index.go"
```

Then, reference it in the module definition with the `Migrations` field, as in the `index.go` file of the previous step. Finally, run the following command in your application's directory:

```bash
go run . db:generate blog
```

The command needs the application's database, as it connects to it. It logs that the migration was generated, and writes the following files in `src/modules/blog/migrations`:

- `Migration<timestamp>.go`: the migration, with the SQL statements it runs to apply and revert the changes.
- `.snapshot-blog.json`: a snapshot of the models' schema. The next time you run the command, it compares your models to the snapshot to find the changes.
- `index.go`: it's rewritten to list every migration of the directory.

<Note>

You can only generate migrations for the modules of your application, whose configuration has a `Resolve` path. Learn more about migrations in the [Migrations chapter](!docs!/learn/fundamentals/data-models/write-migration).

</Note>

### 6. Run Migrations

To create the module's tables in the database, run the following command:

```bash
go run . db:migrate
```

The command runs the pending migrations of every module, syncs the [module links](!docs!/learn/fundamentals/module-links), runs the [loaders](!docs!/learn/fundamentals/modules/loaders) of the modules, and then runs the migration scripts.

## Test the Module

To test the module, resolve its service from the container and use it. The [container](!docs!/learn/fundamentals/medusa-container) gives you the service of the module under its key, in a [route](!docs!/learn/fundamentals/api-routes), a [workflow](!docs!/learn/fundamentals/workflows), or a [script](!docs!/learn/fundamentals/custom-cli-scripts).

For example, create the following script:

```go title="src/scripts/test-blog.go" file="modules/scripts/posts.go" region="test-module"
```

Then, register it by its name in the `Scripts` option of `cli.Run`, as explained in the [Custom CLI Scripts chapter](!docs!/learn/fundamentals/custom-cli-scripts), and run it:

```bash
go run . exec test-blog
```

The script creates a draft with the `CreateDraft` method of your service, lists the posts with the internal service of the `Post` data model, and logs them.
