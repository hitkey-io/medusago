# {metadata.title}

In this chapter, you'll learn what a long-running workflow is and how to configure it.

## What is a Long-Running Workflow?

When you execute a workflow, you wait until the workflow finishes execution to receive the output.

A long-running workflow is a workflow that continues its execution in the background. You don't receive its output immediately. Instead, you subscribe to the workflow execution to listen to status changes and receive its result once the execution is finished.

### Why use Long-Running Workflows?

Long-running workflows are useful if:

- A task takes too long. For example, you're importing data from a CSV file.
- The workflow's steps wait for an external action to finish before resuming execution. For example, before you import the data from the CSV file, you wait until the import is confirmed by the user.

### When is a Workflow Considered Long-Running?

A workflow is also considered long-running if:

- One of its steps has its `Async` and `BackgroundExecution` options set to `true`, as explained in the [next section](#run-a-step-in-the-background).
- One of its [nested workflows](!docs!/learn/fundamentals/workflows/execute-another-workflow) is a long-running workflow.

Since a long-running workflow's execution is stored in the database while it runs, you can view it in the Medusa Admin, as explained in the [Store Workflow Executions chapter](!docs!/learn/fundamentals/workflows/store-executions).

## Change Step Status

Once the workflow's execution reaches an async step that waits for its status, it waits in the background for the step to succeed or fail before it moves to the next step.

To fail or succeed a step, use `composer.SetStepSuccess` and `composer.SetStepFailure`. They find the workflow engine in the container. They're the same operations the Workflow Engine Module's service, registered in the container under the `workflows` key, has.

<Note>

Admin users can also succeed or fail a step with the [Succeed a Step](!api!/admin/workflows-executions) and [Fail a Step](!api!/admin/workflows-executions) API routes.

</Note>

## Access Long-Running Workflow Status and Result

To access the status and result of a long-running workflow execution, use `composer.Subscribe` and `composer.Unsubscribe`, which are also methods of the Workflow Engine Module's service.

The workflow's execution only notifies its subscribers if you execute it with the `Notify` option of `composer.RunOptions`.

To retrieve the workflow execution's details at a later point, you can also [store the workflow's executions](!docs!/learn/fundamentals/workflows/store-executions) with a retention time.

The `EventType` of the event is one of `onBegin`, `onStepBegin`, `onStepSuccess`, `onStepFailure`, `onStepAwaiting`, `onCompensateBegin`, `onCompensateStepSuccess`, `onCompensateStepFailure`, and `onFinish`.

If the `EventType` is `onFinish`, the workflow finished executing. The event then also has a `Result` property holding the workflow's output, and an `Errors` property with the errors that occurred, if any. The result is a JSON-like value: an object is a `*dal.Record`, not the Go type your workflow returns.

### Unsubscribe Function

You can unsubscribe from the workflow using `composer.Unsubscribe`, which accepts the workflow ID, the transaction ID, and the subscriber ID you passed to `Subscribe`.

## Nested Long-Running Workflows

When you execute a long-running workflow within another workflow, the parent workflow becomes a long-running workflow as well. The parent workflow waits for the nested workflow to finish before continuing its execution.

To change the status of an async step of the nested workflow, use the ID of the workflow you executed (the parent) as the `WorkflowID` of the `IdempotencyKey`, with the name of the nested workflow's step as the `StepID`.

Learn more about nested workflows in the [Execute Nested Workflows chapter](!docs!/learn/fundamentals/workflows/execute-another-workflow).

## Workflow Engine Modules

The Workflow Engine Module executes the workflows. MedusaGo comes with two:

- The in-memory Workflow Engine Module, which is the default. It keeps the steps that wait for their status in the memory of the process. If the process restarts, they're lost, and the executions stored in the database stay in their last state.
- The Redis Workflow Engine Module, which stores the checkpoints of executions, so a waiting step can be completed from any instance of your application. Use it in production. Learn how to configure it in the [MedusaGo Configurations chapter](!docs!/learn/configurations/medusa-config).
